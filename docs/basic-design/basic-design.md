# 既存アプリ基本設計書

> 文書の記入項目とID規則は[ドキュメント項目定義](../document-items.md)を参照してください。

## 1. 設計方針

ポータル表示用の固定データをExpressからJSONで提供し、ブラウザー側で検索、画面切替、解決ナビ、メール下書き生成を行います。相談内容はサーバーへ送信しません。

## 5. HTTPインターフェース

| Method | Path | 応答 | キャッシュ |
|---|---|---|---|
| GET | `/` | 日本語のポータルHTML | `no-store` |
| GET | `/assets/portal-core.js` | 共通クライアントロジック | Express静的配信 |
| GET | `/assets/portal.js` | クライアントJavaScript | Express静的配信 |
| GET | `/assets/portal.css` | CSS | Express静的配信 |
| GET | `/api/portal` | ポータルデータJSON | `no-store` |

## 7. 主要フロー

### 7.1 初期表示

1. ブラウザーが`GET /`と静的ファイルを取得します。
2. クライアントが`GET /api/portal`を実行します。
3. 取得中はデータ依存の操作を無効化します。
4. 成功時は各画面を初期化します。
5. 失敗時はエラーと再読込ボタンを表示します。

### 7.2 FAQ検索

1. 利用者がキーワードまたはカテゴリを指定します。
2. クライアントがFAQデータを絞り込みます。
3. 一致するFAQと件数を再描画します。
4. 0件の場合は空状態を表示します。

### 7.3 解決ナビから相談

1. 利用者が症状と回答を選択します。
2. クライアントが回答履歴を保持して次ノードへ進みます。
3. 結果ノードで関連FAQまたは相談を選択します。
4. 相談を選ぶと、カテゴリ、概要、回答履歴を相談画面へ渡します。

### 7.4 メール下書き

1. 利用者が相談カテゴリ、概要、相談内容を入力します。
2. クライアントが文字数と空入力を検証します。
3. 正常時は件名、本文、`mailto:`リンクを生成します。
4. 利用者が内容を確認し、コピーまたはメールアプリを開きます。

## 8. エラー設計

| 状況 | 利用者への結果 |
|---|---|
| ポータルデータ取得失敗 | エラーメッセージと再読込ボタン |
| 取得が10秒を超過 | リクエスト中断後、取得失敗として表示 |
| 相談入力が不正 | 理由を表示し、対象項目へフォーカス |
| クリップボード利用不可 | 手動コピーを案内 |
| 不明な画面ハッシュ | FAQ・ナレッジ画面を表示 |

## 9. 非機能設計

- 画面言語を日本語とします。
- 意味的なHTML、ラベル、ARIA属性、フォーカス表示を使用します。
- 900pxと600pxを境界として画面レイアウトを調整します。
- CSS変数でライト・ダークテーマを切り替えます。
- 相談入力はブラウザー内だけで扱います。
- ポータルデータと画面HTMLはキャッシュせず配信します。
