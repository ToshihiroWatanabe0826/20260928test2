# テスト規約

## 1. 目的

この文書は、簡易ハンズオンで単体・結合・システムテストを実施するときの最低限のゴールを定義します。

## 2. 共通ルール

- 変更した機能と、影響を受ける既存機能を対象にする。
- テストケースを要件IDまたは設計IDへ対応付ける。
- 実行したコマンド、期待結果、実測結果を記録する。
- 実行日時、対象の実装Commit SHA、実行コマンド、終了コード、成功・失敗・未実施件数を、各テスト仕様書の`実施証跡`へ追記する。チャットやPull Request本文だけの報告で完了扱いにしない。
- UT・ITは標準出力と標準エラーを含む実行ログを、各工程の`docs/<工程>/evidence/`配下へ保存し、仕様書から参照できるようにする。
- STはPlaywrightの実行ログと、主要な利用者シナリオを明示的に撮影した画面画像を`docs/system-test/evidence/`配下へ保存する。失敗時だけの自動撮影で代替しない。
- 証跡ファイルにはトークン、秘密情報、個人環境の絶対パスを残さない。
- 未実施、失敗、確認不能の項目を成功扱いにしない。
- 仕様を判断できない場合は、期待結果を推測せず確認する。

## 3. 単体テストのゴール

- 変更した関数・モジュールについて、該当する正常・異常・境界値を少なくとも1件ずつ確認する。
- 外部連携から分離できる処理を対象にし、同じ条件で再実行できるようにする。
- 追加・変更したロジックのLine Coverageは80%以上を目標とする。
- Coverageを計測できない場合は未計測と記録し、実施したケースで代替しない。
- 関連する単体テストがすべて成功したことを確認する。

## 4. 結合テストのゴール

- API、画面、データ、モジュール間の連携について、正常系とエラー系を少なくとも1件ずつ確認する。
- HTTPステータス、応答内容、更新後のデータが基本設計と一致することを確認する。
- 不正な入力や更新が拒否され、元のデータが維持されることを確認する。
- 関連する結合テストと既存テストが成功したことを確認する。

## 5. システムテストのゴール

- 追加した機能の主要な利用者シナリオを、要件の受け入れ条件に沿って確認する。
- 正常な操作と、入力・更新に失敗した場合の表示を少なくとも1件ずつ確認する。
- 既存ポータルの主要機能が引き続き利用できることを確認する。
- 自動または手動の確認方法と実測結果を記録し、確認できない項目は未確認とする。
